# v1.2.0 verification record

Measured on 2026-09-09, aarch64 macOS 26.6.2. Baseline: `ee70701`.
The release is prepared locally; the tag and release are not published.

## Build and integration evidence

| Toolchain | Debug tests | ReleaseSafe tests | Examples / fuzz / docs | Packaged consumers | Compile-error fixtures |
| --- | --- | --- | --- | --- | --- |
| Zig 0.15.2 | 1090 passed | 1090 passed | passed | both passed | 6 passed |
| Zig 0.16.0 | 1090 passed | 1090 passed | passed | both passed | 6 passed |
| Zig 0.17.0-dev.356+3140b375f | 1090 passed | 1090 passed | passed | both passed | 6 passed |

There are 13 compiled examples and nine compiled fuzz targets. Each independent
consumer has two tests and obtains serde through `b.dependency`. The packaging
check copies only the `.paths` allowlist into a temporary tree. It checks the
published guides and license as well as consumer compilation/execution.

Zig 0.15.2's linker did not resolve arm64 symbols in the host's default macOS 26.5
SDK, whose stubs advertise arm64e. Selecting the installed macOS 15.4 SDK for
`xcrun --sdk macosx --show-sdk-path` let the compiler build and run without SDK-specific repository changes. This was a process-local SDK selector, not a source or global SDK
change. Zig 0.16.0 and master used the default SDK.

The library tests and the three new integration suites also compile in ReleaseSafe
for `x86_64-linux-gnu` and `x86_64-windows-gnu` using Zig 0.16.0
(`zig test -fno-emit-bin`). This is compilation evidence, not execution on those OSes.
The existing CI matrix still runs tests on Linux, macOS and Windows for all three
compiler selections. Its remote result remains a release gate after an authorized
push; no remote CI result is claimed here.

`zig build interop` passed on the local Erlang installation: 22 OTP-to-Zig terms
and eight Zig-to-OTP terms. `zig build example-managed-json` printed the parsed
value and `WrongType at /age (1:23)` for the intentionally invalid example.

## Commands

```sh
zig build test
zig build test -Doptimize=ReleaseSafe
zig build examples fuzz docs
python3 test/check_compile_errors.py
python3 test/check_package.py
zig build interop
zig fmt --check src/ bench/ test/ examples/ build.zig
```

Repeat the build and integration commands using the listed compiler versions;
Zig 0.15.2 on this particular host requires the SDK selection described above.
The diagnostics suite includes prefix-corpus parity, aliases/flatten, tag replay,
custom hooks/adapters, Unicode/CRLF, tiny buffers, and injected allocation failures.
A zero-capacity allocator test confirms diagnostic state needs no heap allocation.

## Performance

Benchmarks use Zig 0.16.0, ReleaseFast, the existing seven-sample harness and
its `smp` allocator. The first complete sweep contains 56 ordinary cases plus
three opt-in diagnostic cases. Raw results: [baseline](benchmarks/v1.2.0-baseline.json),
[current](benchmarks/v1.2.0-current.json), and [sequential repeats](benchmarks/v1.2.0-repeats.json).

The initial sweep flagged nested serialization at +10.15%; its three sequential
baseline/current confirmation pairs measured -0.30%, +1.19%, and -0.25%.
Wide64 deserialization measured +8.06% in the full sweep and +14.04%, +4.53%, and
+3.00% in confirmation pairs (median +4.53%). Thus individual outliers exceeded
10%, but a sustained regression above 10% did not reproduce. Results are local
measurements subject to compilation warm-up, scheduling and CPU frequency changes;
CI measurements on the target hosts remain relevant.

The repeated comparisons used the same current harness in both trees through
`bench/prepare_baseline.py`; diagnostics are omitted when the old library lacks
the API. The helper also raises the baseline's comptime budget for wide structs,
without changing the measured runtime algorithm.

| JSON parsing case | Ordinary ns/op | Diagnostics ns/op | Opt-in overhead |
| --- | ---: | ---: | ---: |
| 64-field struct | 1462.329 | 2642.500 | about 81% |
| Nested struct | 201.090 | 230.500 | about 15% |
| Array of structs | 746.069 | 887.600 | about 19% |

These approximate opt-in figures use the first full sweep. They include path
maintenance even on success. Ordinary APIs carry no diagnostic state. Allocation
freedom of the diagnostic state is tested separately with a zero-capacity allocator;
these CPU benchmarks reuse an arena and do not measure first-use arena allocation.

```sh
# In a disposable checkout of ee70701:
python3 /path/to/current/bench/prepare_baseline.py .
zig build bench -Dbench-format=json -Dbench-out=/tmp/serde-baseline.json
# In the current tree:
zig build bench -Dbench-format=json -Dbench-baseline=/tmp/serde-baseline.json \
  -Dbench-out=/tmp/serde-current.json
# Use a stable output filename to reuse the compiled binary for confirmation:
zig build bench -Dbench-filter=json.wide64.deserialize.serde.cpu \
  -Dbench-format=json -Dbench-out=/tmp/serde-wide.json
```

Run confirmation commands sequentially in each tree, with matching flags and no
other compilation or benchmark jobs running.

## Limits

Long-running fuzz execution and complete specification conformance suites were
not run. They remain explicitly outside the v1.2 release scope. Cross-platform
execution must be confirmed by CI before publishing; master results identify the
installed snapshot and cannot guarantee future Zig compiler revisions.
